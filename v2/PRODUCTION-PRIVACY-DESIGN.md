# V2.0 正式隐私与本机加密方案（设计评审草案，不是已交付功能）

**适用边界**：用户只用 iPhone，希望优先 Face ID、失败时本机 PIN 备用；必须免费优先、原件及历史数据无损，不允许擅自升级生产系统或写入真实病院数据。

## 目前的证据与限制

独立预览端 `preview-privacy.js` 是 **仅合成测试的可选 PIN 界面遮挡**，不加密 IndexedDB / File / CacheStorage。它阻挡了当前预览主页与当前发布的两类备份入口，但**不能将其当成原生 Face ID、安全边界或正式隐私保障**。恶意同源脚本、旧版离线缓存页面、开发者工具、浏览器存储和已被控制的设备可能绕过此类前端遮挡。必须保持真实数据禁止接入。

## 技术方案的强制条件

1. **先确认数据加密模型，而不是只做弹窗**。工作台业务记录、附件原件和离线暂存需要一致的客户端密文保护；云端现有 AES-GCM 只保证已上传密文，不能代替本地静态加密。
2. **区分认证与解密**。WebAuthn / Passkey 可以让操作系统触发平台用户验证，但 WebAuthn 成功本身不自动提供应用数据解密密钥。仅有本地 JS 判断、屏幕遮罩、PIN 哈希均不足以保护加密密钥。
3. **iPhone 端技术验证优先**。分别在 Safari 浏览器与“添加到主屏幕”的 PWA 检查 WebAuthn 平台凭据、`userVerification='required'`、PRF 扩展或等效可实际导出密钥材料的能力（如可用且有清晰的安全模型），不假设所有 iOS 版本均支持。若不能可靠实现硬件背书的解密，不宣称 Face ID 加密已落地。
4. **PIN 备用安全模型**。6位数字 PIN 熵不足，不能在缺乏系统级强制限速的情况下独立包装本机长期加密密钥；如果选择数字 PIN，只能明示为 UI 防窥或与可验证的系统硬件保护组合。真正离线恢复使用高强度独立恢复密码或高熵恢复密钥，密文备份必须先校验后恢复。
5. **失效安全**。后台切换立即锁、90秒无操作自动锁、启动前关闭敏感渲染；身份、密钥或资源验证异常必须保持锁定，并确保用户可通过安全恢复流程取回原件，不建议“清除浏览器数据”作为修复办法。
6. **不让任何一端自动覆盖另一端**。设备离线期间的记录与附件始终保留，采用原有修订版本/哈希协议；冲突需要逐项人工确认，保留双方加密历史及附件。
7. **备份与灾难恢复先行**。单独加密的可离线保存备份应包含记录、原件、历史快照、校验摘要及恢复所需但不公开的密钥封装；验收流程必须能在全新隔离库完成逐字节恢复，不依赖单一设备仍然登录。

## 本轮已证明的基础能力（不在正式系统启用）

- 已创建与现有业务库完全隔离的 `privacy-crypto-poc.js`：独立随机名称 IndexedDB、AES-GCM-256 密文记录与二进制原件、PBKDF2-SHA256 封装数据密钥、原件元数据与名称加密、带认证清单的加密备份、加密密文和还原后数据核对、恢复密码轮换。
- 已创建 `privacy-shadow-poc.js`：仅本机测试环境、合成业务源只读核验，先比对全部业务记录/队列/原件，再复制至新加密库并恢复至另一个隔离库。严禁用在真实数据或公共预览环境。
- 自动化 Chromium 和 WebKit 验证：本轮 `66 PASS / 0 FAIL`，参见 [GitHub Actions](https://github.com/wangxueqing0427-oss/personal-workbench/actions/runs/43379683018)。额外攻击用例测试证明异编号密文调包无法解密；旧备份在密钥更新后仍保留旧恢复密码的访问能力，设计中要单独对用户说明。
- 这项 PoC 证明密码派生和本地密文存储可以走通，但**没有实现 Face ID 解密密钥、尚未替换正式 `WorkbenchBusinessStore`、未读取任何用户手机上的原 V1 数据**；不能据此开放正式业务。

## 分块加密阶段已完成的实验验证（仅合成资料）

- 新增独立的 `privacy-sharded-store-poc.js` 和 `test-privacy-sharded-store-poc.cjs`，V2 原业务界面无需改写，即可使用分离的 AES-GCM 加密业务状态、独立队列修订记录、独立加密附件目录和每块256KiB的附件原件密文。
- 6MiB+39B 的合成扫描件上传后产生25个密文块，完整回读与独立隔离备份恢复的 SHA-256 一致。常规医院编辑既不重加密也不全量读取已有原件块；双窗口首次创建/续写冲突、附件中途事务中止、被修改/删除的密文块、超过16MiB的附件都会失败并保留旧记录、队列及原件。

## 独立业务对象加密试验进展（未用于正式版）

- 在此前完整业务状态单记录原型及256KiB附件分块原型基础上，新建 `privacy-object-store-poc.js`，把医院、项目、记录、库存、出入库、耗材订单及文件引用拆为**逐条加密对象**。对象身份 AAD 绑定业务类型、UUID和对象修订号；修改单个医院可实测只更新该医院的密文，其他项目、订单及原始附件块都不重新加密。
- 加密目录、变化对象、同步队列版本和新附件分块在同一个 IndexedDB 事务中执行 CAS；写入失败、对象缺失、密文调包、未来不支持的数据字段、缺失附件、错误恢复密码都停止处理且保留旧数据。备份前要求最新加密队列快照与逐条解密合成业务记录完全一致。
- 最新[自动化全部通过记录](https://github.com/wangxueqing0427-oss/personal-workbench/actions/runs/43389466913)：Chromium **104/104**、WebKit **104/104**，合计208项通过、0失败，其中逐条加密专项各28项。报告见 `v2/OBJECT-ENCRYPTION-REVIEW-2026-11-13.md`。
- **生产缺口仍然明确**：读取当前业务状态时还要解密所有对象；每个离线队列新作业仍存储一份完整业务状态（仅加密而非增量），会增加存储占用；对象类别与UUID索引在本地库中是明文元数据；尚未接入这个对象加密方案的跨设备云端同步、硬件生物识别密钥解封或真实iPhone验收。此代码只在本机合成自动化中执行，没有进入公共预览资源。

## 加密增量队列原型已完成（仍未连接真实云端）

- 新增独立 `privacy-delta-journal-poc.js`，只将本次发生变化的业务对象密文追加到对应修订的加密队列日志，避免每次编辑都重复持久化整份医院、项目及跟进记录。
- `queueData()` 可以依靠加密差量从0号版本依次回放，重新构造原接口预期的每一版业务 `snapshot`；历史修订顺序、缺号、篡改的密文、对象ID重复、与当前对象状态不一致，均要求失败而不写回。现阶段禁止静默删除或重新排序旧业务对象。
- [最终Chromium+WebKit自动化记录](https://github.com/wangxueqing0427-oss/personal-workbench/actions/runs/43390258735)：Chromium135项、WebKit135项，合计270项通过、0失败（含之前全部兼容回归）；[独立预览构建门禁](https://github.com/wangxueqing0427-oss/personal-workbench/actions/runs/43390281569)绿色，未部署该实验模块。详细审计见 `v2/DELTA-JOURNAL-REVIEW-2026-11-13.md`。
- **仍缺的能力**：回放会在内存重建每条旧版本完整状态，需要检查点和按需解压；单个医院/项目的按需查询优化；云端身份、双设备加密增量同步和冲突恢复；目标iPhone平台生物识别/密钥保管；正式版迁移与用户终验。

## 双独立浏览器端到端加密同步原型（新进展）

- 新增仅本机合成试验专用的 `privacy-e2e-cloud-poc.js`。两台隔离的移动端模拟浏览器，使用各自的 IndexedDB 和逐对象加密库，通过一个本机模拟 Worker 协议的 HTTP 服务交换**二次 AES-GCM 加密的完整归档**。本机增量日志与云端传输仍是两层不同的技术：**当前云端上传的是完整密文归档，并非每次只上传变化对象**。
- 模拟服务按原 Worker 的 `expectedRevision / expectedHash / payload.hash` CAS 规则和密文分片 manifest 工作，服务器只存不透明密文和不可变历史；客户端从服务读取后先验哈希及密文，再恢复至新数据库。任何冲突先保留本地和远端的独立副本，不自动覆盖。
- 通过双设备断网补传、两个设备分别增加医院后显式批准安全合并、同一医院双方更改时拒绝自动合并、已完成上传但ACK丢失的幂等重试、上传过程中网络断开重新发送密文分片、恢复早期历史版本及不安全令牌/远端哈希拒绝。
- [最新完整 Chromium+WebKit 复测](https://github.com/wangxueqing0427-oss/personal-workbench/actions/runs/43397336843)：每引擎169项通过，**共338项通过、0失败**（含以前所有兼容回归），双端云端模拟专项各34项。模拟云端6个历史版本，122次分片上传及2次重复分片确认；[公开预览构建隔离预检](https://github.com/wangxueqing0427-oss/personal-workbench/actions/runs/43396918957)通过，没有部署这些实验模块。
- **正式交付仍有重要缺口**：尚未连接真实Cloudflare Worker测试身份、未验证真正 iPhone Face ID/PWA、没有安全的设备配对和密钥分发、没有生产可用的原件增量云传输及同一业务对象的人工冲突解决界面。技术审核见 `v2/LOCAL-E2E-CLOUD-REVIEW-2026-11-13.md`。

## 零损坏迁移次序

- 只读审计旧版 V1.5.7 / 现有 V2 预览的记录和本地文件来源，先列明已检查的**设备 / 域名 / Safari / PWA**范围，不能拿一个浏览器本地数据代替全设备。
- 对每条旧业务记录、全部附件二进制、历史版本计算 SHA-256 与数量/总字节；得到完整快照，缺原件或不一致时**停止**。
- 在隔离数据区建立加密副本，不写旧数据库；解密回读与快照逐条逐字节核对后，方可将新版本交给用户最终验收。
- 真正投入使用时也保留完整可恢复旧快照、正式回滚路径及用户明确确认，不自动删除旧图标、旧存储、云端原件或旧业务数据。

## 下一阶段实施顺序及验收门槛

**P0**：确定 iOS Safari/PWA 可验证的解密密钥保管与 Face ID 方案，完成威胁模型和本机加密 PoC（仅合成数据）。然后开发多端同步身份的非明文安全发放方式、离线缓存升级和强制失败阻断。  
**P1**：对真实 iPhone 进行一次完整最终验收：Face ID/PIN、锁屏/后台、离线重开、文件逐字节完整性、备份/隔离恢复、双设备冲突以及安装到主屏幕数据边界。  
**P2**：另行获得用户批准后，才考虑实际医院资料迁移、V1/V2 正式切换或生产部署。

不得为了满足进度而用预览 PIN 遮挡冒充 Face ID + 本机加密已交付。项目目前**不需要用户实际操作**，直到真实 iPhone 终验或必须授权的步骤为止。
