# V2.0 正式隐私与本机加密方案（设计评审草案，不是已交付功能）

**适用边界**：用户只用 iPhone，希望优先 Face ID、失败时本机 PIN 备用；必须免费优先、原件及历史数据无损，不允许擅自升级生产系统或写入真实病院数据。

## 目前的证据与限制

独立预览端 `preview-privacy.js` 是 **仅合成测试的可选 PIN 界面遮挡**，不加密 IndexedDB / File / CacheStorage。它阻挡了当前预览主页与当前发布的两类备份入口，但**不能将其当成原生 Face ID、安全边界或正式隐私保障**。恶意同源脚本、旧版离线缓存页面、开发者工具、浏览器存储和已被控制的设备可能绕过此类前端遮挡。必须保持真实数据禁止接入。

## 技术方案的强制条件

1. **先确认数据加密模型，而不是只做弹窗**。工作台业务记录、附件原件和离线暂存需要一致的客户端密文保护；云端现有 AES-GCM 只保证已上传密文，不能代替本地静态加密。
2. **区分认证与解密**。WebAuthn / Passkey 可以让操作系统触发平台用户验证，但 WebAuthn 成功本身不自动提供应用数据解密密钥。仅有本地 JS 判断、屏幕遮罩、PIN 哈希均不足以保护加密密钥。
3. **iPhone 端技术验证优先**。分别在 Safari 浏览器与“添加到主屏幕”的 PWA 检查 WebAuthn 平台凭据、`userVerification='required'`、PRF 扩展或等效可实际导出密钥材料的能力（如可用且有清晰的安全模型），不假设所有 iOS 版本均支持。若不能可靠实现硬件背书的解密，不宣称 Face ID 加密已落地。
4. **PIN 备用安全模型**。6位数字 PIN 熵不足，不能在缺乏系统级强制限速的情况下独立包装本机长期加密密钥；如果选择数字 PIN，只能明示为 UI 防窥或与可验证的系统硬件保护组合。真正离线恢复使用高强度独立恢复密码或高熵恢复密钥，密文备份必须先校验后恢复。
5. **失效安全**。后台切换立即锁、90秒无操作自动锁、启动前关闭敏感渲染；身份、密钥或资源验证异常必须保持锁定，并确保用户可通过安全恢复流程取回原件，不建议“清除浏览器数据”作为修复办法。
6. **不让任何一端自动覆盖另一端**。设备离线期间的记录与附件始终保留，采用原有修订版本/哈希协议；冲突需要逐项人工确认，保留双方加密历史及附件。
7. **备份与灾难恢复先行**。单独加密的可离线保存备份应包含记录、原件、历史快照、校验摘要及恢复所需但不公开的密钥封装；验收流程必须能在全新隔离库完成逐字节恢复，不依赖单一设备仍然登录。

## 本轮已证明的基础能力（不在正式系统启用）

- 已创建与现有业务库完全隔离的 `privacy-crypto-poc.js`：独立随机名称 IndexedDB、AES-GCM-256 密文记录与二进制原件、PBKDF2-SHA256 封装数据密钥、原件元数据与名称加密、带认证清单的加密备份、加密密文和还原后数据核对、恢复密码轮换。
- 已创建 `privacy-shadow-poc.js`：仅本机测试环境、合成业务源只读核验，先比对全部业务记录/队列/原件，再复制至新加密库并恢复至另一个隔离库。严禁用在真实数据或公共预览环境。
- 自动化 Chromium 和 WebKit 验证：本轮 `66 PASS / 0 FAIL`，参见 [GitHub Actions](https://github.com/wangxueqing0427-oss/personal-workbench/actions/runs/43379683018)。额外攻击用例测试证明异编号密文调包无法解密；旧备份在密钥更新后仍保留旧恢复密码的访问能力，设计中要单独对用户说明。
- 这项 PoC 证明密码派生和本地密文存储可以走通，但**没有实现 Face ID 解密密钥、尚未替换正式 `WorkbenchBusinessStore`、未读取任何用户手机上的原 V1 数据**；不能据此开放正式业务。

## 新增：原业务界面接入加密存储接口验证（合成数据）

- 已编写独立实验适配器 `privacy-business-adapter-poc.js`，直接连接现有 `business-ui.js` 和 `business-core.js`，不修改业务功能源文件。医院数据、附件原件和待同步队列统一封装为一次 AES-GCM 加密且 CAS 的快照，证明基本的事务原子性。
- [最新自动测试记录](https://github.com/wangxueqing0427-oss/personal-workbench/actions/runs/43381628535)：Chromium **53/53**、WebKit **53/53**，共106项通过。原始业务界面新增医院、保存合成附件、文件字节完整性、备份恢复、冲突写入和异常回滚均有测试证据。
- **不发布这个适配器到已有 Worker**：目前只是单行快照试验，单文件2MiB、合成原件累计4MiB且每次编辑都需要重新加密全量数据。正式版必须改成分对象/分块加密并保持跨记录、队列与原件的事务一致性；并且完整接入加密同步及系统身份密钥方案。
- 独立审查详见 `v2/ENCRYPTED-BUSINESS-ADAPTER-REVIEW-2026-11-13.md`；实验代码没有读取真实设备或旧库数据，不等于可迁移或可上线。

## 零损坏迁移次序

- 只读审计旧版 V1.5.7 / 现有 V2 预览的记录和本地文件来源，先列明已检查的**设备 / 域名 / Safari / PWA**范围，不能拿一个浏览器本地数据代替全设备。
- 对每条旧业务记录、全部附件二进制、历史版本计算 SHA-256 与数量/总字节；得到完整快照，缺原件或不一致时**停止**。
- 在隔离数据区建立加密副本，不写旧数据库；解密回读与快照逐条逐字节核对后，方可将新版本交给用户最终验收。
- 真正投入使用时也保留完整可恢复旧快照、正式回滚路径及用户明确确认，不自动删除旧图标、旧存储、云端原件或旧业务数据。

## 下一阶段实施顺序及验收门槛

**P0**：确定 iOS Safari/PWA 可验证的解密密钥保管与 Face ID 方案，完成威胁模型和本机加密 PoC（仅合成数据）。然后开发多端同步身份的非明文安全发放方式、离线缓存升级和强制失败阻断。  
**P1**：对真实 iPhone 进行一次完整最终验收：Face ID/PIN、锁屏/后台、离线重开、文件逐字节完整性、备份/隔离恢复、双设备冲突以及安装到主屏幕数据边界。  
**P2**：另行获得用户批准后，才考虑实际医院资料迁移、V1/V2 正式切换或生产部署。

不得为了满足进度而用预览 PIN 遮挡冒充 Face ID + 本机加密已交付。项目目前**不需要用户实际操作**，直到真实 iPhone 终验或必须授权的步骤为止。
