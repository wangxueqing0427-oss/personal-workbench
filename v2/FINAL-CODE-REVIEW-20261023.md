## 4. 发现的非阻断局限（不可隐藏）

### R1 / P2：空本地队列不主动获取远端新版本

`offline-sync.js` 的 run 遍历本地 jobs。jobs=[] 时不会读远端，status 的“已同步”来自已有 meta。无网络的 VM 探针传入已配置身份、已确认版本10和空队列，实际 fetch 调用0、状态仍“已同步”，证实它不是持续双向拉取。

已有界面披露“0项不等于全部设备一致”，所以本轮不把它作为新的数据覆盖缺陷；**但这是正式跨设备同步前必须补齐的功能缺口**。不能把当前通过的一次上传/合并验收扩展成“其他设备的修改会自动来到本机”。不应为了审查全绿临时改变同步逻辑；本轮未改。

### R2 / P2：历史首次接入脚本绑定活跃云端固定记录数

`test-first-device.cjs` 即使 `MERGE_CAPTURE_REPLAY=1`，也先 GET 当下共享云端，之后仍断言34条/版本9。已核实的历史服务器证据是版本10/35条；因此这个脚本默认重跑会碰到历史固定期望，而不是代表现有数据损坏。之前记录的26+26通过属于其当时快照，不能标成当前重跑通过。

正式接入 CI 前，应改为明确的、私有冻结版本9夹具或独立生成测试数据，禁止清空共享云端来迁就断言。本轮仅记录问题，没有访问共享数据或放宽断言。

### R3 / P2：可移植自动化/CI门禁尚未建成

测试依赖当前 Windows 用户下的 runtime-loader 和已下载浏览器；没有便携依赖清单/自动 CI 门禁，部分历史备份/Worker日志以运行输出记录，而不是每项都有独立报告文件。不能让机器上的一次通过等同于任意开发机重现通过。需在后续受控测试工程工作中解决，不阻止将明确受限的原型归档到开发分支。

这些是允许合并“开发原型基线”的已披露限制，不是允许真实业务上线的豁免。
