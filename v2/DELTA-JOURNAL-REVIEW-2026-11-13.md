# V2.0｜逐对象加密增量日志原型审核（2026-11-13）

## 审核范围与严格隔离

新增 `v2/privacy-delta-journal-poc.js` 及 `v2/test-privacy-delta-journal-poc.cjs`，在先前逐条加密业务对象的基础上，**仅在全新 127.0.0.1/localhost 浏览器、随机加密试验库和合成数据标记下启用**。当前工作台 V1.5.7、生产 `main`、原 V2 staging、Cloudflare 公开 Preview Worker 与真实医院数据未改动，未新增服务费用。

## 解决的问题

先前每次医院资料小改动，虽然只重加密变化的医院对象，但离线队列的每个版本都会保存整份（已加密）业务状态。如果持续出差离线记录，这些完整快照会快速膨胀。

此次原型将 **队列持久化** 改为单独 AES-GCM 加密的差量记录，每项包含：
- 当前修订号和基线修订号（用于重放顺序与丢失检测）；
- 发生改变的医院/项目/跟进/耗材订单/库存/文件引用对象，只有这些变化对象的值参与该次加密；
- 任务 ID、创建时间、当前工作流状态及尝试次数；**不在数据库队列条目中反复保存整份业务快照**。

读取旧有 `WorkbenchOfflineSync` 风格的 `queueData()` 接口时，在内存中从0号版本开始，按顺序重放每个版本的差量，重新构造每条任务需要的 `snapshot`；内存回放后还与逐条加密对象当前状态核对，不一致则失败而不是宣布云端已同步。所有差量、单条业务对象、版本头、附件目录、256KiB附件密文块仍使用原先带 AAD 的 AES-GCM + 单一 IDB 事务 CAS。

为保持安全，**这版原型禁止删除/重排既有对象**；由于旧版业务 UI 的测试路径不需要删除，能够避免差量日志遗漏必要的删除事件。如果未来需要删除/重排，必须显式增加可验证的删除日志/排序事件、保留历史版本并增加回归测试，不得直接解除这一限制。

## 本轮增加的攻击与回归用例

- 真实 V2 手机业务界面初始化、增加医院、保存6MiB合成原件、确认跟进等操作仍可正常使用。
- 每次快照可根据差量日志独立重建，第0~4号修订版本完整且最后一版与实际逐条加密业务记录一致。
- 修改单个医院的最新日志密文体积应显著小于同版本整个业务状态的 JSON 字节；原件依然在独立块中，不重复存进日志。
- 直接在 IndexedDB 中篡改一个旧版本差量密文后，`queueData()` 和完整加密备份均必须拒绝重放/导出。
- 旧分块事务测试、文件逐字节一致性、失联后的本地队列、首次与后续并发冲突、异常回滚、对象调包和文件恢复保持兼容回归。
- **真实云端跨设备 E2E 尚未接入此模块**。这里的“队列恢复”是本机可重放加密日志，不等于线上 Worker 已确认收到资料或可安全跨设备合并。

## 已知阻断项

1. `queueData()` 当前仍会把每个历史版本重建为完整内存快照，随着修订历史增长可能增加解密运算与峰值内存占用；未来应采用周期性加密检查点和增量任务的按需展开。
2. 业务对象仍需在 `read()` 时全部解密读取；未来需实现逐医院/项目读取缓存和增量列表的安全一致性。
3. 文件原件16MiB单份、最多50份、队列200条及其他人工测试限额没有解除；真实医院业务、DICOM目录等不能用此原型直接处理。
4. Face ID/硬件密钥、安全 PIN 备用、真正 iPhone Safari/PWA 测试、云端端到端同步身份、旧真实数据迁移，均尚未完成。
5. 这个实验使用合成测试口令和WebCrypto，不能抵御已经控制同源JavaScript、设备环境的攻击者；苹果系统能力需真实 iPhone 才能最终核实。
6. **本轮独立自动化验证已绿色完成，但只覆盖当前模拟与合成场景**。后续代码每次改变仍必须重新运行两套浏览器和预检，不能沿用旧的绿色结果。
